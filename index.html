System 01

Multi-agent orchestration

The problem

One founder, three parallel workstreams — a web app, two mobile apps, and a go-to-market operation — and no way to be in three places at once. Hiring wasn't an option. The work had to be delegated to something.

What I built

A multi-agent orchestration system on Claude Code. A CTO orchestrator whose tools dispatch six typed engineer roles — frontend, backend, AI, mobile, DevOps and QA — with MCP server integrations and filesystem-based memory, so each agent gets governed access to the tools and systems of record it needs.

  • Concurrent fan-out with per-run turn caps, so one runaway task can't consume the whole budget.
  • Per-run transcript logging for every agent, which turned out to matter more than I expected.
  • Sequential fallback with backoff on rate-limit errors, so a throttled run degrades instead of failing.
  • Structured-output hardening on every model response: re-prompt with the malformed payload in context, then brace-extraction fallback, then throw — with field validation after parsing.
  • A tiered safety filter that runs deterministic blocklists and regex first and escalates to a fast model only on ambiguous signals — deliberately fail-closed on the deterministic tier, fail-open on the ambiguous one.

What broke

A multi-day agent run crashed with its results sitting only in ephemeral storage. Recovery meant replaying tool calls out of the subagent transcripts — the logging I'd added for debugging turned out to be the only reason the work was recoverable at all. 31 of 31 files reconstructed clean.

The standing rule since: never let an agent run write its only copy of anything to ephemeral storage.
System 02

AI GTM pipeline

The problem

A two-sided marketplace needs businesses before it needs anything else. Buying a lead list gets you records; it doesn't get you records that are real, open, in the right place, and worth contacting. I needed a pipeline that could tell the difference — at a scale I couldn't check by hand.

The architecture

  • Stage 1 — enrichment. Vendor pull, selected on cost-per-result rather than a subscription upgrade for what was a one-time job.
  • Stage 2 — ICP screen. Nine parallel screening agents emitting KEEP / CUT / BORDERLINE with reasons, so every judgment call was auditable rather than a black box.
  • Stage 3 — verification. Per-record web verification against a closed-enum schema with no blanks — explicit NOT_FOUND and UNVERIFIED literals instead of empty cells, because an empty cell is indistinguishable from a failure.
  • Scored and graded on a 0–100 model with A/B/C/D grading over four connected data layers, extended into a Clay and Python pipeline.
  • Outreach infrastructure across Clay, HubSpot, Instantly and Apify, with deliverability gating before send.

Human approvals

Agents never sent anything. The pipeline produced a graded, reasoned set; sending stayed a human decision. Every BORDERLINE verdict carried its reasoning so I could overrule it on the record.

What I got wrong, and what it taught me

  • A scraper's result limit turned out to be per username, not per run — 48 seeds at a limit of 120 returned 928 results. The smoke test had verified the vendor accepted the parameter, never what it meant. Fix: bound the run itself, don't check headroom before it.
  • An enrichment join keyed on positional index against a file another process was appending to, silently attaching records to the wrong businesses. Rule written: never index-join a file another process can append to.
  • A source-quality finding that changed the method — a review site's "closed" banner proved unreliable, and a dead domain turned out not to be evidence of closure. I re-ran a closure audit with the suspect source disallowed: zero prior calls overturned.
  • A stubborn pass-rate ceiling that looked like a bug was a property of the segment, not a defect. I made the falsifiable prediction that sourcing more owners would lower the rate, and it did.
System 03

Payments & money path

Two systems, six years apart

At Link Munch I built and shipped a point-of-sale line that processed menu orders and payments end to end through the apps, piloted with a first group of restaurants. At Dossiay I built the marketplace money path on Stripe. Different problems, same discipline: the money path is the one place where "mostly correct" is indistinguishable from broken.

How the ledger works

  • Append-only, and it refuses any write without an idempotency key. Entries are written in a transaction with a conditional existence check, plus a separate marker row in the same transaction — so a retried charge cannot double-post.
  • Store credit spends through one atomic operation. The balance check and the debit are the same conditional update, so concurrent spends can't oversell a balance.
  • A single writer for money. Funding is marked only from the Stripe webhook, never the HTTP path, so a retried webhook can't restart a clock.
  • Taken from test mode to live, including Connect Express payouts and Stripe Tax — the latter built around a hard API constraint, since automatic_tax isn't valid on PaymentIntents. The flow became calculate → charge → create-from-calculation on the success webhook.

The bug that justified all of it

A founder reported one thing: "my balance didn't change." It turned out to be four separate defects — full-coverage credit zeroed the card charge, the server then rejected it under Stripe's minimum, the purchase silently never happened, and a later earnings view didn't net refunds.

I fixed both the client and the server sides deliberately, to protect clients running stale code, then verified end to end against live test mode by reading the ledger rows directly rather than trusting the UI.

Knowing what not to answer

Working through marketplace-facilitator tax status, I got far enough to understand the question properly and then flagged it for a CPA rather than guessing. Being able to tell the difference between a problem you should solve and one you should escalate is part of the job.
